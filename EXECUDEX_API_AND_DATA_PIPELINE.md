# Execudex: API Integration & Data Pipeline (Technical Reference)

**Purpose:** This document describes how Execudex acquires, processes, stores, and displays political intelligence — with emphasis on Mistral AI, other external APIs, Supabase edge functions, database tables, and the React Native app screens that consume the data.

**Audience:** Engineers or reviewers (e.g. Claude) who need a complete picture of the software pipeline without reading the entire codebase.

**Last updated:** July 2026 (based on current repository state)

---

## 1. Executive Summary

Execudex is a React Native / Expo mobile app backed by **Supabase** (PostgreSQL + Storage + Edge Functions). The app does **not** call Mistral or Tavily directly from the client. All AI and web-acquisition work happens in **Supabase Edge Functions** (Deno/TypeScript), which:

1. Search and extract web content (Tavily, direct fetch, Jina Reader proxy)
2. Store raw text in Supabase Storage (`web` bucket) with metadata in `web_content`
3. Call **Mistral AI** (`mistral-small-latest`, sometimes `mistral-large-latest`) to extract, classify, summarize, and generate structured outputs
4. Write results to PostgreSQL tables (`ppl_index`, `ppl_profiles`, `legi_index`, `legi_profiles`, `card_index`, `card_content`, `questions`, etc.)
5. The mobile app reads those tables and renders cards, synopses, metrics, and Q&A

The core product pattern is **evidence-centric**: generated content is tied to stored source text, not free-form LLM output.

## 3. Core Data Model

### 3.1 Index tables (entity registry)

| Table | Purpose |
|-------|---------|
| `ppl_index` | Politician registry: name, tier (`hard`/`soft`/`base`), `indexed`, `weak`, office metadata |
| `legi_index` | Legislation registry: bill name, `indexed`, `weak`, `data_update` freshness |

### 3.2 Profile tables (summaries / metrics)

| Table | Purpose |
|-------|---------|
| `ppl_profiles` | AI synopsis (`synopsis`, `agenda`, `identity`, `affiliates`), approval/disapproval metrics, poll data |
| `legi_profiles` | Bill overview text, legislative metadata |

### 3.3 Card tables (modular knowledge units)

| Table | Purpose |
|-------|---------|
| `card_index` | Card metadata: `title`, `subtext`, `screen`, `category`, `score`, `link`, `web` (storage path), `owner_id`, `is_ppl`, `is_active` |
| `card_content` | Full card body: `body_text`, `tldr`, `link1`, `excerpt`, `related`, `legi_text` |

**Screen values (politicians):** `agenda_ppl`, `identity`, `affiliates` (+ category for sub4 pages)

**Screen values (legislation):** `agenda_legi`, `impact`, `discourse`

### 3.4 Evidence tables

| Table / Storage | Purpose |
|-----------------|---------|
| `web_content` | Metadata for stored source pages: `owner_id`, `is_ppl`, `path`, `used` flag |
| Supabase Storage `web` bucket | Raw extracted page text (`.txt` files, often chunked at ~110k chars) |

### 3.5 Interaction tables

| Table | Purpose |
|-------|---------|
| `questions` | Card Q&A: `card_id`, `question`, `answer` (generated by Mistral from card source) |
| Bookmarks / history | User engagement (client-side + Supabase) |

## 4. External APIs — Roles and Usage

### 4.1 Mistral AI

**Endpoint:** `POST https://api.mistral.ai/v1/chat/completions`

**Models used:**
- `mistral-small-latest` — default for most tasks (search decisions, synopsis, card gen, Q&A, bill overview)
- `mistral-large-latest` — used in `ppl_card_gen` when source text exceeds ~110,000 characters

**Typical parameters:**
- Temperature: 0.1–0.3 (low, for factual extraction)
- Timeouts: 90s–180s depending on function
- Output: structured JSON or constrained plain text

**Functions that call Mistral:**

| Edge Function | Mistral role |
|---------------|--------------|
| `ppl_search` | Decide if search results match user query; extract person metadata (office, party, state) |
| `ppl_round1` | Domain quality judge for unknown URLs (allow/deny with JSON verdict) |
| `ppl_synopsis` | Generate politician synopsis from Wikipedia + web corpus |
| `ppl_card_gen` | Extract card title/subtext/category from stored page text |
| `ppl_affiliates` | Generate affiliate/related profile suggestions |
| `ppl_metrics` | Poll/metrics synthesis |
| `bill_search` | Bill matching and metadata extraction |
| `bill_overview` | Structured bill overview JSON |
| `bill_cards` | Generate legislation cards from bill text |
| `bill_coverage` | Generate discourse/coverage cards |
| `card-questions` | Answer user questions using **only** the card's source page text |
| `full_card_gen` | Unified card body generation (body_text, tldr, demographics tagging) |
| `impact_gen` | Personalized "how this affects you" text per user + card |
| `records_update` | Process voting records data |

### 4.2 Tavily

**Endpoints:**
- `POST https://api.tavily.com/search` — web search
- `POST https://api.tavily.com/extract` — page content extraction (markdown or text)

**Used by:** `ppl_search`, `ppl_round1`, `ppl_round2`, `ppl_synopsis`, `bill_search`, `bill_text`, `bill_update`, `records_open`, `records_update`, and others.

**Pattern:** Search → filter by allowed domains → extract → store in `web` bucket → insert `web_content` row.

### 4.3 Congress.gov / VoteSmart / direct HTTP

- `bill_text` fetches bill text from Congress.gov (Tavily extract + direct fetch fallback)
- `bill_update` scrapes congress.gov/most-viewed-bills
- `records_open` / `records_update` target VoteSmart key-votes pages (Jina proxy when direct fetch returns 403)

### 4.4 Jina Reader (optional)

`records_open` uses `https://r.jina.ai/{url}` when VoteSmart blocks edge-function IPs.

### 4.5 Expo Push

Several generation functions (`ppl_card_gen`, `bill_cards`, etc.) send push notifications when long-running generation completes.

## 6. Politician Flow (Complete)

### 6.1 Discovery — User searches for a politician

**App:** `app/(tabs)/home.tsx` calls `POST /functions/v1/ppl_search` via `fetch()` (not `functions.invoke`) with query + office filter.

**`ppl_search` pipeline:**
1. Normalize query (common name handling)
2. Tavily search + Wikipedia fetch
3. Scrape/extract candidate pages (concurrency-limited)
4. **Mistral:** `mistralDecide()` — pick best match from corpus
5. **Mistral:** `mistralExtractPerson()` — office type, party, state, incumbent status
6. Upsert `ppl_index` row; cache content in Storage
7. Return ranked results to app

### 6.2 Profile open — First-time indexing

**App:** `NavigationService.navigateToPoliticianProfile()` → `PoliticianProfileService.handleProfileOpen()` → navigates to `app/index1.tsx` (tab shell with Synopsis + sub1–sub3).

**Pre-navigation steps:**
1. `check_profile_access` — quota enforcement (weekly profile limit for free tier)
2. Profile processing (if `ppl_index.indexed !== true`):

| Step | Service / Function | What it does |
|------|-------------------|--------------|
| 1 | Check `ppl_profiles` + `ppl_index.indexed` | Skip if already indexed |
| 2 | `profile_index` | Create initial profile row from cached web content |
| 3 | `ppl_synopsis` | **Mistral** generates synopsis/agenda/identity/affiliates text → `ppl_profiles` |
| 4 | Mark `ppl_index.indexed = true` | Profile ready for display |

**Note:** Metrics (`ppl_metrics`) are no longer auto-run on open; triggered manually from `see-more.tsx`.

### 6.3 Synopsis display

**App:** `app/profile/synop.tsx`

Reads from:
- `ppl_index` — name, records status, weak flag
- `ppl_profiles` — synopsis, agenda, identity, affiliates, approval/disapproval

Shows "Generate New Cards" button when profile is not weak and has zero cards (`CardGenerationService.shouldShowGenerateButtonForSynopsis`).

### 6.4 Card generation (on-demand)

**Orchestrator:** `services/cardGenerationService.ts`

**User trigger:** "Generate" buttons on `sub1` (Agenda), `sub2` (Identity), `sub3` (Affiliates), `sub4` (category pages), or synopsis.

**Generation logic (`generatePoliticianCards`):**

```
1. Check web_content for unused rows matching page/category
   └─ If found → ppl_card_gen(politicianId, webIds)
2. Else → ppl_round2(politicianId, [keyword])  // Tavily search + store
   └─ Then → ppl_card_gen(politicianId)
```

**`ppl_round2` (content acquisition):**
- Tavily search per category keyword
- Domain allowlist enforcement (large list in function; mirrors `PPL_ALLOWED_DOMAINS.md`)
- Extract, chunk, store to `web` bucket
- Insert `web_content` rows with `used = false`

**`ppl_card_gen` (card creation):**
- Load unused `web_content` paths from Storage
- **Mistral** per page: extract title (≤10 words), subtext (≤20 words), category, score
- Enforce tier-based category sets (hard vs soft/base)
- Insert `card_index` rows; mark `web_content.used = true`
- Does **not** call `full_card_gen` — the client invokes `full_card_gen` when the user opens a card (via `CardService`)
- May send Expo push on completion

### 6.5 Card listing (grid view)

**App screens:** `app/profile/sub1.tsx`, `sub2.tsx`, `sub3.tsx`, `sub4.tsx`

**Data fetch:** `utils/cardData.ts` → `fetchCardsByScreen()` queries `card_index` filtered by:
- `owner_id` = politician ID
- `is_ppl = true`
- `screen` = mapped page value (`agenda_ppl`, `identity`, `affiliates`)
- `is_active = true`

Cards displayed as pressable grid tiles (title + subtext preview).

**Search within page:** `searchCardsForPage()` filters `card_index` client-side by title/subtext/category substring → navigates to `/results`.

### 6.6 Card detail (full view)

**App:** `app/profile/sub5.tsx`

**On open:**
1. Fetch `card_index` (metadata)
2. Fetch `card_content` (body_text, tldr, link1, excerpt)
3. `trackCardOpen()` — analytics
4. Optionally invoke `impact_gen` for personalized impact text

**Displayed sections:**
- Subtext (large card header)
- Body text (~730–740 chars)
- TLDR (~130–140 chars)
- Source link pill (link1)
- Personal Impact (from `impact_gen` if generated)
- Q&A button → `/card-questions`
- Related profiles button (if `related` field populated)

### 6.7 Card Q&A

**App:** `app/card-questions.tsx`

**Submit flow:**
1. User types question (max 200 chars)
2. `supabase.functions.invoke('card-questions', { question, card_id })`
3. Edge function:
   - Regex moderation (profanity, hate speech, must look like a question)
   - Load `card_index.web` path
   - Download source text from Storage
   - **Mistral:** answer using ONLY source text, max 55 words
   - Insert into `questions` table
4. App refreshes Q&A list from `questions` table

### 6.8 Newly generated cards showcase

**App:** `app/new-gen.tsx`

After batch generation, app navigates here with `cardIds` param. Fetches those cards from `card_index`, resolves owner names from `ppl_index`/`legi_index`, lets user tap into `sub5`.

### 6.9 Records (voting history)

**App:** `app/records.tsx`, `app/profile/synop.tsx`

- `records_open` — Tavily/Jina acquire VoteSmart key-votes content → Storage
- `records_update` — **Mistral** processes voting record data → updates profile records fields

## 7. Legislation Flow (Complete)

### 7.1 Discovery — User searches for a bill

**App:** `home.tsx` calls `POST /functions/v1/bill_search` via `fetch()`.

**`bill_search` pipeline:**
1. Expand bill code variants (e.g. `hr7340` → `H.R. 7340`, etc.)
2. Tavily search (Congress.gov, VoteSmart domains)
3. **Mistral** for bill matching and metadata
4. Upsert `legi_index`; store bill text in Storage
5. Return results to app

### 7.2 Profile open — First-time indexing

**App:** `NavigationService.navigateToLegislationProfile()` → `LegislationProfileService.handleProfileOpen()` → navigates to `app/index2.tsx` (tab shell with Overview + legi1–legi3).

| Step | Function | What it does |
|------|----------|--------------|
| 0 | Re-run `bill_search` (enrich mode) | Only when `bill_status = 'processing'` **and** `data_update` is > 5 days old |
| 1 | Check `legi_index.indexed` | Skip processing if already indexed |
| 2 | `profile_index` | If `bill_lvl` missing or storage incomplete — fetches Congress.gov synopsis via Tavily/Mistral |
| 3 | `bill_overview` | **Mistral** generates overview → `legi_profiles` (if overview missing/invalid) |
| 4 | Mark `legi_index.indexed = true` | Client-side after overview step |

**Not run on mobile profile open:** `bill_text`, `bill_cards`, `bill_coverage`. Those are on-demand (Overview / legi tab Generate buttons) or via the batch `legislation_profile_processor` edge function (not invoked by the app today).

**Low materiality:** Returned when the user triggers `bill_cards` or `bill_coverage` and content is thin; `index2.tsx` / `CardGenerationService` handle `suggest_ui` hints.

### 7.3 Legislation screens

Shell route: `app/index2.tsx` (tabs). Individual tab components live under `app/legislation/`.

| App screen | DB screen value | Generation function |
|------------|-----------------|---------------------|
| `app/overview.tsx` (Overview tab in index2) | — | Reads `legi_profiles`; first-time **Generate New Cards** calls `bill_cards` directly |
| `legi1.tsx` (Agenda) | `agenda_legi` | `bill_cards` via `generateAgendaCards` |
| `legi2.tsx` (Impact) | `impact` | `bill_cards` via `generateImpactCards` |
| `legi3.tsx` (Discourse) | `discourse` | `bill_coverage` via `generateDiscourseCards` |
| `legislation/overview.tsx` | — | Alternate/legacy overview component (used by `index3.tsx`, not the main legislation flow) |

Per-tab Generate button visibility (`CardGenerationService`):
- **legi1:** unused `web_content` with path containing `billtext`
- **legi2:** unused `web_content` with path containing `coverage` *(see red-flag note below — `bill_cards` reads `billtext`/`synopsis`, not `coverage`)*
- **legi3:** unused `web_content` with path containing `coverage`

Overview **Generate New Cards** shows when profile is not `weak` and has zero cards (`shouldShowGenerateButtonForOverview`).

### 7.4 Card display

Same pattern as politicians: grid on legi1–legi3 → `sub5.tsx` or `legi5.tsx` for detail.

## 8. Card Content Deep Generation

### `full_card_gen`

Called after `card_index` row exists. Uses **Mistral** to produce:
- `body_text` — main explanatory paragraph
- `tldr` — short summary
- `excerpt` — pull quote
- Demographics tagging (age, gender, state, political standing) via keyword matching + LLM

Writes to `card_content` table linked by `card_id`.

### `impact_gen`

Called from `sub5.tsx` / `legi5.tsx` when user views a card.

Inputs: `card_id`, `user_id`

Uses **Mistral** + user onboarding demographics to generate personalized impact text stored on the card or returned inline.

## 11. Tier System & Content Policy

Politicians have tiers (`hard`, `soft`, `base`) stored in `ppl_index.tier`. Tier is computed in `profile_index` (limit-score rubric), not `profile_labeling`.

**Category allowlists differ by tier** (enforced in `ppl_card_gen`):

- **Hard tier:** Full category sets per screen + `more` category
- **Soft/Base tier:** Reduced category sets; no `more` category

**Card quotas** (legacy — enforced in Python test tooling and `PPLDataService.calculateQuotaDeficits`, but **not** in live `ppl_card_gen` or client generate buttons):
- Hard: ~180 cards
- Soft: ~72 cards
- Base: ~30 cards

The client always shows Generate on sub-pages (`shouldShowGenerateButtonForPage` returns `true`). Synopsis/overview buttons hide when `weak = true` or cards already exist.

**Freshness:** 7-day card pruning was part of older generation logic; current `ppl_card_gen` does not prune by age. Metrics refresh uses a 21-day manual cooldown (`PoliticianProfileService.generateMetricsManually`).

**Evidence requirement:** Cards must cite source material (except metrics categories).

**Weak profiles:** `profile_labeling` sets `weak = true` when content is insufficient; generate buttons hidden on synopsis/overview.

## 12. Domain Governance

`ppl_round1` and `ppl_round2` enforce a large **allowlist** of trusted domains (government, major news, research orgs). Unknown domains go through **Mistral domain judge** (`_mistralJudgeSmall`) returning JSON: allow/deny, reliability score, reason.

Explicit **denylist** blocks paywalled or unreliable extraction targets.

This is a key trust/control mechanism: the pipeline prefers known-good sources over open-web chaos.

## 14. Error Handling & Operational Patterns

- **Concurrency pools:** Edge functions use configurable `CONCURRENCY`, `POOL_LIMIT` values
- **Run budgets:** `ppl_round2` has `RUN_BUDGET_MS` (default 25s) to avoid edge timeouts
- **Graceful degradation:** `NavigationService` continues on access-check **errors** (fail-open), but blocks navigation when access is explicitly denied
- **Low materiality:** Legislation pipeline returns `suggest_ui` hints when content is thin
- **Abort controllers:** Client services support cancellation during long operations
- **Push notifications:** Long-running generation notifies user on completion

---

## 15. What the App Does NOT Do

- **No direct Mistral/Tavily calls from the mobile client** — all AI/search is server-side
- **No offline generation** — cards require network + edge function execution
- **No unbounded chat** — Q&A is per-card, source-grounded, 55-word max answers
- **No automatic full profile generation on every open** — indexed profiles skip processing

## 18. Review Prompts (for Claude or other reviewers)

Suggested questions to evaluate this architecture:

1. **Evidence chain:** Is the `web_content` → `card_index.web` → Storage → Mistral path consistently auditable?
2. **Failure modes:** Where do timeouts, empty extractions, or Mistral JSON parse failures leave the UI?
3. **Tier enforcement:** Are soft/base category restrictions correctly applied at generation time and display time?
4. **Quota vs. generation:** Does unlimited on-demand card generation conflict with subscription profile quotas?
5. **Security:** Are service-role keys and API secrets properly isolated from the client?
6. **Grounded Q&A:** Is 55-word, source-only Q&A sufficient guardrail, or are there bypass risks?
7. **Domain governance:** Is the allowlist + Mistral judge approach maintainable at scale?
